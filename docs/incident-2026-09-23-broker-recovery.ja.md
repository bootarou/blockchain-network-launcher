# 2026-09-23 ノード異常停止とbroker復旧の調査記録

作成日: 2026-09-24

本書は、Windowsの再起動後にbrokerが起動しなくなった事象について、原因の根拠、データの構造、実際に成功した復旧方法を説明するものです。
ユーザー提供のログ、コマンド出力、バックアップ調査結果を基にしています。
**過去の作業記録であり、記載したパスに対して復旧操作を再実行するためのスクリプトではありません。**

新しく実装したBNLの復旧機能の操作・制限は、[Local Chain Recovery](local-recovery.md)を参照してください。

## 1. 結論

今回、起動を直接妨げていたのは、**brokerが処理すべき通知が残っているという管理情報に対して、通知ファイルの実体が欠けていたこと**です。

最初の失敗は `spool/block_change` のメッセージ欠損でした。その後、異常終了した復旧処理の `recovery.lock` が残り、次の起動ではロック取得にも失敗しました。
したがって、ロックファイルは問題のすべてではなく、**先行する復旧失敗に続いて発生した、もう一つの起動障害**でした。

一方、元のノードに残っていたブロックは、高さ148874までimporterで再実行できました。
このブロックを使って、コピー上でノードの状態と通知キューを再構築し、brokerから新しいMongoDBへ反映することで復旧しました。

今回行ったのは、次の方式です。

```text
残存するローカルブロック
  -> コピー上でブロックを再実行
  -> ノードの状態とbroker向け通知を再構築
  -> 新しいMongoDBを構築
  -> 検証
  -> 元データを退避して切り替え
  -> ブロック処理・ファイナライズの再開を確認
```

**ネメシスだけに戻す初期化でも、別ノードからの再同期でも、障害後ZIPからの復元でもありません。**

## 2. 確認できたことと、まだ分からないこと

| 区分 | 内容 | 根拠・留意点 |
|---|---|---|
| 発端として報告された事実 | BNLとノードの稼働中にWindows Updateによる再起動が発生 | ユーザーからの状況報告 |
| 確認済みの直接原因 | キューの管理位置が未処理メッセージを指す一方、そのファイルが存在しない | 起動ログと停止中のファイル確認 |
| 確認済みの二次的障害 | 復旧処理の異常終了後、`recovery.lock` の取得に失敗 | 同じログ内のエラー発生順序 |
| 確認済みの復旧可能性 | ローカルブロックから高さ148874まで再実行でき、状態ハッシュが一致した | importer終了コード0、ハッシュ照合 |
| 合理的な推定 | 異常停止を境に、キューの位置情報とファイル実体の整合性が崩れた | 発生状況とディスク上の不整合はこの説明に整合する |
| 未確定 | ファイルの作成・削除・位置更新のどの永続化がどの順序で途切れたか | ログだけでは特定できない |
| 未確定 | Windows、WSL、Docker、ファイルシステム、Catapultのどの層に問題があったか | 更新履歴、停止シーケンス、I/Oの追加調査が必要 |
| 別に確認した問題 | 障害後に作成されたZIPの一部エントリーに読み取り・ヘッダー不整合があった | ZIP自体の信頼性の問題。生成・転送・保存のどの段階かは未確定 |

「Windows Updateがきっかけだった」ことと、「Windows Updateの特定の不具合がファイルを壊した」と断定することは別です。
また、**元のMongoDBや全ブロックが壊れていたと断定したわけでもありません。**
MongoDBは、再生成する通知との整合性を確実にするため、新しく作り直しました。

## 4. ブロック・状態・キュー・DBは別のデータ

同じネットワークの情報でも、保存場所と役割は異なります。

| データ | 代表的な保存場所 | 役割 |
|---|---|---|
| ブロック本体 | `data/00000/*.dat` など | ネットワークで確定・受理してきたブロックの履歴 |
| ブロックに付随するstatement | 同じグループの `*.stmt` | レシートや解決情報などに関わるブロック付随情報 |
| ノードの状態 | `data/state`、`data/statedb` | ブロックの実行結果を蓄積した状態。履歴そのものとは異なる |
| 通知キュー | `data/spool/*` | ノード側の更新をbrokerなどへ渡すためのファイルベースの通知 |
| MongoDB | 今回は `databases/db` | brokerが反映し、RESTが検索・参照するデータ |
| ロックファイル | `server.lock`、`broker.lock`、`recovery.lock` | プロセスの多重起動防止などに用いる実行管理情報 |
| 投票関連データ・鍵 | `data/voting`、`voting_status.dat`、`votingkeys` など | 投票・署名に関わる情報。単なる再生成可能キャッシュとして扱わない |

概念的には、次の関係です。

```text
ノードがブロックを処理
  +--> ブロック保存
  +--> ノードの状態を更新
  +--> spoolに通知を出力
         +--> brokerが通知を読む
                +--> MongoDBに反映
                +--> 通知の配信

RESTはノードとMongoDBを利用してAPIを提供
```

これは各データの役割を示す図であり、ディスクへの書き込み順序を保証する図ではありません。
複数の保存先があるため、異常停止後には「ブロックが残っている」ことと「通知・DBまで完全に整合している」ことを分けて確認する必要があります。

## 5. 起動ログをどう読んだか

`message.txt` の最初の重要なエラーは次のものでした。

```text
repairing spooling, commit step 2
repairing importance
repairing messages
reading from file queue failed due to missing message file
./data/spool/block_change/0000000000024589.dat
```

続いて、`catapult.recovery` が異常終了しています。

```text
Aborted (core dumped)
!!!! broker recovery has CRASHED!
```

次の起動では、次のエラーになりました。

```text
LockOpen failed: 17
could not acquire instance lock "./data/recovery.lock"
```

重要なのは、**「ロック取得失敗」より前に「必要な通知ファイルがない」という失敗が記録されている**ことです。

```text
必要なキューメッセージが見つからない
  -> 通常のクラッシュ復旧処理が異常終了
  -> recovery.lockが残る
  -> 次の起動はロック取得でも止まる
```

ロックだけ削除しても、欠けたメッセージの内容は戻りません。
逆に、プロセスが動いている状態でロックを消すと、多重起動などを防ぐ仕組みを損なうおそれがあります。

## 6. キューの数値が示していた不整合

停止中の元データで、次の値を確認しました。

| 対象 | 位置・高さ |
|---|---:|
| `data/index.dat` のブロック高 | 148874 |
| `spool/block_change/index.dat` | 148874 |
| `spool/block_change/index_broker_r.dat` | 148873 |
| `spool/state_change/index.dat` | 297748 |
| `spool/state_change/index_broker_r.dat` | 297746 |
| `spool/state_change/index_server.dat` | 297748 |

### 6.1 block_change

ここでのキュー位置は、読み取り側が次に読む位置と、書き込み側の次の位置です。
今回、読み取り側は `148873`、書き込み側は `148874` だったので、管理情報上は1件の未処理メッセージが必要でした。

キューファイル名は16進数です。

```text
148873 (10進数) = 24589 (16進数)
必要なファイル: 0000000000024589.dat
```

ところが、ディレクトリには位置情報ファイルだけがあり、このメッセージファイルはありませんでした。
これはログのエラーパスと一致します。

### 6.2 state_change

`297748 - 297746 = 2` なので、管理情報上は2件の未処理メッセージが必要です。
こちらも、停止中の確認ではメッセージファイルがありませんでした。

### 6.3 数字を混同しない

- ブロック高、通知キューの位置、ファイナライズエポックは別の値です。
- 今回の `block_change` の書き込み位置とブロック高が同じでも、キュー番号を一般にブロック高と同一視してはいけません。
- `state_change` がブロック高の2倍だったことも、あらゆる構成・履歴で常にそうなる保証ではありません。
- 読み終わったメッセージファイルが消えていること自体は正常です。問題は、**まだ必要な範囲のファイルがない**ことです。
- 稼働中の位置情報とディレクトリ一覧を別々のタイミングで読むと、処理の進行による見かけの差が出ます。今回の欠損判断は停止中のデータで行いました。

## 7. なぜ単純な対処を選ばなかったか

| 対処案 | 今回採用しなかった理由 |
|---|---|
| `recovery.lock` だけ削除 | 通知の欠損を修復できない |
| 読み取り位置を強制的に進める | 未反映の通知を飛ばし、DBとノード状態の不整合を隠す可能性がある |
| 欠けた番号の空ファイルを作る | 通知の内容がないので、有効なメッセージにはならない |
| MongoDBだけ空にして再起動 | 消費済みの過去の通知がすべて残っているわけではなく、全履歴の再反映を保証できない |
| ノード状態だけを削除して再起動 | 通知・DBとの整合を含めた復旧手順になっていない |
| ネメシスに戻して別ノードから同期 | もう一台は同期途中で、最新までの履歴を取得できる保証がなかった |
| 障害後のZIPだけを頼りに復元 | 障害状態を含む可能性に加え、ZIP自体にも不整合が見つかっていた |

特に、ネットワークの最新データを持つ唯一のノードを初期化すると、その後の同期先が存在しなくなる可能性があります。
「ネットワークにつなげば必ず元に戻る」とは限りません。

## 8. なぜローカルブロックから復旧できたか

今回使った `catapult.importer` は、既存のローカルブロックを読み、ブロックの処理結果を再構築するために使用しました。
ネメシスから状態を作り、今回のログでは高さ2以降のブロックを順に読み込んでいます。

今回の重要な設定は次のとおりです。

| 設定 | 確認した値・役割 |
|---|---|
| `dataDirectory` | `./data`。コピーしたディレクトリで作業 |
| `fileDatabaseBatchSize` | `1` |
| `enableCacheDatabaseStorage` | `true` |
| `enableVerifiableState` | `true`。再計算した状態ハッシュを照合 |
| importerで使う `extension.filespooling` | `true`。通知キューを再生成 |
| importerで使う `extension.mongo` | `false`。この段階でMongoDBを更新しない |
| importerで使う `extension.zeromq` | `false` |

importerは今回、`server-config` 側の `config-extensions-recovery.properties` を使いました。
ファイル名に `recovery` とあっても、実行したバイナリは `catapult.importer` です。

**失敗していた `catapult.recovery` と、今回成功した `catapult.importer` は同じ処理ではありません。**
前者は残っているコミット状態・通知などを使った通常の復旧で止まり、後者ではコピーから旧状態・旧通知を退避したうえで、ブロック履歴を再実行しました。

なお、ブロックが欠けている、必要なネットワーク設定が合わない、といった場合にも成功する方法ではありません。

## 9. 実際に行った復旧の流れ

### 9.1 元データを停止状態で保全

ノード・broker・DBの状態とマウント先を確認し、元のノードディレクトリとMongoDBを別の作業領域へコピーしました。
ブロックデータのサンプル、保存高、空き容量、importerの存在も確認しました。

この時点では、元のノードデータを書き換えていません。

### 9.2 コピー側の派生データを退避

コピーしたノードの `data` から、次のものを作業領域の `before-import` へ移しました。
存在するものだけが対象です。

```text
state / state.tmp / statedb / spool / importance
server.lock / broker.lock / recovery.lock
commit_step.dat / server-recovery.started
```

ブロック、statement、ファイナライズ証明関連データなどは残しました。
投票データ・投票状態・鍵・証明書も、安易に初期化しない方針を取りました。

「壊れた可能性のある状態の続きを使う」のではなく、「保全した履歴を入力にして状態を作り直す」ための準備です。

### 9.3 importerでブロックを再実行

`bnl-recovery-importer` をネットワークなしで実行しました。
高さ148874まで処理し、終了コード0、OOMによる終了なしを確認しました。

ログ上の `load blockchain` は `12981057ms`、約3時間36分でした。
これはその処理区間の実測であり、他のPCの所要時間や、復旧作業全体の時間を保証する値ではありません。

### 9.4 再構築結果を再度コピーしてbroker検証用に分離

importerの結果を `broker-test-v2` にコピーしました。
これにより、brokerがキューを読み進めてファイルを消費しても、importer直後のコピーを別に残せました。

途中でSSHが切れたため、コピーは `docker run -d` で起動した専用コンテナへ移しました。
`COPY_COMPLETE` と終了コード0を確認してから次へ進みました。

`docker stats` の `BLOCK I/O` が0でも、コピー未進行とは断定できませんでした。
今回はコピー先の使用量、`cp` プロセスの状態、CPU時間、最後の完了マーカーも合わせて確認しました。

### 9.5 新しいMongoDBを初期化

本番と分離した内部Dockerネットワーク上で、空のMongoDBを初期化しました。
ポートはホストへ公開せず、既存のMongoDB初期化スクリプトでコレクションとインデックスを作りました。

最初の試行では、初期化スクリプトが相対パスを解決できずに失敗しました。
`/docker-entrypoint-initdb.d` を作業ディレクトリに指定した新しい試行で初期化が成功しました。
失敗したDBディレクトリを、正常に初期化済みのDBとして再利用することは避けました。

### 9.6 brokerで通知をDBに反映

検証用brokerは、コピー側のノードデータと新しいMongoDBだけに接続しました。
brokerは再生成された通知を読み、DBを構築しました。

brokerは常駐プロセスなので、キューの処理が終わっても通常は `running` のままです。
**importerの「終了コード0」と、brokerの「稼働しながらキュー処理完了」は、別の完了条件です。**

### 9.7 整合性と再起動を検証

次の節のハッシュ・件数・キュー位置を照合しました。
検証用brokerとMongoDBは正常停止・再起動も確認し、再度正常停止して切り替えに備えました。

### 9.8 元のデータとDBを組として切り替え

手動作業では、切り替え中の操作競合を避けるため `symbol-manager` も停止しました。
元データは削除せず、`original-before-cutover` に退避しました。
その後、再構築した `data` とMongoDBを元のパスへ移しました。

同一ファイルシステム内のディレクトリ移動を使い、SSH切断に備えて `systemd-run` で実行しました。
途中の通常エラーでは元に戻す処理も用意しました。
ただし、**ノードデータとDBの二つの移動が、電源断に対して一つの原子的処理になるわけではありません。**

サービスが `running` の間の `Result=success` だけでは完了とせず、`SubState=exited` と独立した `CUTOVER_COMPLETE` のログを確認しました。

### 9.9 元の構成で順に起動

```text
元のdbを起動し、件数と末尾ハッシュを照合
  -> 元のbrokerを起動
  -> api-node-0を起動
  -> rest-gatewayを起動
  -> RESTのヘルスとチェーン進行を確認
  -> symbol-managerを起動
  -> BNLともう一台のノードでも進行を確認
```

検証用コンテナのマウント元を移した後は、それらを再起動しないようにしました。
旧パスの再作成や、別データへの誤接続を避けるためです。

## 10. 復旧成功を判断した具体的な証拠

### 10.1 キューの処理完了

再構築後の検証用データでは、次のように読み書き位置が一致しました。

| キュー | 書き込み位置 | broker読み取り位置 |
|---|---:|---:|
| `block_change` | 148874 | 148874 |
| `state_change` | 297748 | 297748 |
| `finalization` | 208 | 208 |

ここでの `finalization` の208も、通知キューの位置です。
RESTの `finalizationEpoch` が208だったことと同じ意味ではありません。
再構築前と通知回数が異なる可能性があるため、元のキュー位置へ数字を無理に合わせる必要もありません。

### 10.2 ブロックハッシュの照合

高さ148874のブロックについて、元データに保存されたBlockElementのハッシュと、再構築DBの `meta.hash` が一致しました。

```text
13771DA20D475B7349F9AF6949A705A44F196098BB5B670C5E73CBA02D2FA013
```

元ファイルは、今回の保存形式では次のパスでした。

```text
data/00014/08874.dat
```

ブロックのディレクトリ分割は10進数の10000単位です。
キューファイル名の16進数表現と混同してはいけません。

この照合で読み取ったのはファイルに格納されたブロックハッシュであり、`.dat` ファイル全体を新たにSHA-256した値ではありません。
また、この比較だけをもって全ブロックの署名を独立検証したとは言いません。

### 10.3 状態ハッシュの照合

importerが高さ148874で計算した状態ハッシュと、末尾ブロックの `block.stateHash` が一致しました。

```text
946BDAE58413F9C36E9A3D2422C5F61DB4284698218FEE1EFE326816DC521E42
```

ブロックの識別情報だけでなく、**ブロックを実行して得たノード状態が、末尾ブロックの記録と一致した**ことが重要です。
ただし、これはMongoDBの全ドキュメントから状態ハッシュを独立再計算した検査ではありません。

### 10.4 DB件数

再構築・切り替え時点で確認した値です。

| 項目 | 件数・高さ |
|---|---:|
| ブロック件数 | 148874 |
| 末尾ブロック高 | 148874 |
| アカウント件数 | 212 |
| トランザクション件数 | 7718740 |

アカウント・トランザクション件数は、再構築結果と切り替え後DBの一致確認にも使用しました。
障害前の独立した完全な件数記録との照合ではありません。

### 10.5 ノード・REST・新しいブロックの処理

元のノードの起動ログで、次を確認しました。

```text
loaded blockchain (height = 148874, ...)
Unlocked harvesting account with result Success_New
```

RESTでは次の応答を確認しました。

```json
{"status":{"apiNode":"up","db":"up"}}
```

その後、MongoDBの末尾が148878となり、RESTでも148879、148881、148885などへ進みました。
単に過去のDBが読めるだけでなく、新たなブロック処理とDB反映が再開していることを確認できました。

### 10.6 ファイナライズの再開

起動直後は次の状態でした。

```text
finalizationEpoch = 208
finalizationPoint = 31
finalized height = 148852
```

後の確認で、次へ進みました。

```text
chain height = 149096
finalizationEpoch = 209
finalizationPoint = 1
finalized height = 149068
```

確定済みブロックのハッシュは次の値でした。

```text
E43E7EB2A6D5E5C901BD3FEB97ECD9279EFE899CDA095145CAC044396D04D7C9
```

最後に、ユーザーからBNL画面ともう一台のノードでも同期進行を確認したとの報告がありました。
もう一台の同期完了や、両ノードの同一高さでのハッシュ照合まで実施した記録はありません。

## 11. 何を復旧できたと言えるか

今回確認できたのは、ローカル履歴に基づく状態・DBの再構築と、ネットワークとしての稼働再開です。

一方、未承認トランザクション、一時的な失敗通知、配送途中の外部通知など、**ブロックに記録されない一時情報まで全部復元できたとは言えません。**
また、ZIP破損の原因調査が完了したわけでもありません。

「復旧成功」は、この確認範囲を伴う判断です。

## 12. 保存しておくべき作業データ

今回の手動作業ディレクトリ内には、用途の異なるコピーがあります。

| パス末尾 | 用途・切り替え後の状態 |
|---|---|
| `node` | importerで再構築した側のチェックポイント |
| `mongo-original` | 最初に保全した元のMongoDBコピー |
| `before-import` | コピー側から退避した旧状態・旧キューなど |
| `broker-test` | SSH切断を挟んだ初期のコピー先。完成済みとは扱わない |
| `broker-test-v2` | broker検証に使用。`data` は切り替え時に元ノード側へ移動済み |
| `mongo-rebuilt` | 最初のMongoDB初期化で失敗した作業領域 |
| `mongo-rebuilt-v2` | 検証済みDB。切り替え時に元DBパスへ移動済み |
| `original-before-cutover/node-data` | 切り替え直前の元ノードデータの実体 |
| `original-before-cutover/mongo-db` | 切り替え直前の元MongoDBの実体 |

今後の手動操作で配置が変わっている可能性があるため、削除・移動の前には必ず現物を確認してください。
**復旧後の正常なバックアップを作り、検証するまでは退避データを削除しない**ことが基本です。

## 13. 新しいBNL復旧機能との関係

今回の成功手順を基に、BNLへコピー上でのローカル再構築機能を追加しました。

| 項目 | 今回の手動作業 | 新実装 |
|---|---|---|
| 操作の継続 | SSH切断対策としてdetachedコンテナやsystemdを使用 | HTTP応答を待ち続けないバックエンドジョブ、状態のポーリング |
| 作業コピー | importer後にbroker用コピーをもう一つ作成 | 基本は一つの作業コピーでimporterからbrokerまで進行 |
| 元データの扱い | 切り替えまで保持 | 同様に保持。自動削除しない |
| 競合操作の防止 | 切り替え時にmanagerを停止 | managerは稼働させ、更新系APIを制限 |
| 切り替え | 手動確認後、停止中に実行 | 検証完了後の明示的な確認操作 |
| 中断時 | 状況を個別に確認 | 状態を記録し、切り替えが曖昧な場合は手動確認が終わるまで操作を制限 |

**手動手順が実機で成功したことと、新実装の全工程を実機で検証済みであることは別です。**
文書作成時点では、新実装は関連テスト28件、型チェック、画面ビルド、PC・スマートフォンの画面操作確認を通過しています。
Docker処理を含む全工程については、検証用Linux環境での実機試験が必要です。

実装はまず、非PQCの指定1.0.3.9イメージ、MongoDB 5.0.15、単一 `api-node-0` 構成などに限定しています。
詳細は[機能仕様と制限](local-recovery.md)を参照してください。

## 14. 今後の運用上の対策

### 停止と再起動

- OS更新などの計画停止では、更新前にノードを正常停止し、関連コンテナの停止結果を確認する。
- brokerの処理待ちとDBへの反映を考慮し、強制終了に頼らない停止手順・猶予時間を検証する。
- 再起動後はコンテナの `running` だけでなく、RESTヘルス、ブロック高、ファイナライズを確認する。
- 異常停止後に何度も起動・ロック削除を繰り返す前に、ログと元データを保全する。

### バックアップ

- 障害後のバックアップは、その時点の障害状態も保存する。正常時の世代も保持する。
- DBとノードデータの整合したバックアップを取得する。停止中の取得が今回の運用では分かりやすい基準になる。
- ZIPの作成成功・ダウンロード成功だけでなく、アーカイブ全体の読み取り検査と隔離環境での復元試験を行う。
- 転送前後のSHA-256一致は、転送で変わっていないことの確認になる。ただし、生成時点で破損しているZIPの正常性は証明しない。
- 大容量のバックアップ作成とダウンロードを分離すると再ダウンロードしやすくなるが、それだけでZIP破損の原因が解消したとは判断しない。

### 冗長化と空き容量

- 最新まで同期した別ノードを維持する。「もう一台ある」だけでなく、その到達高さを確認する。
- 別ノードのDBを安易にコピーせず、設定・鍵・履歴・投票状態との関係を確認する。
- 復旧時は元データ、新しい状態、再生成キュー、新DBを同時に保持するため、通常稼働時より大きな空き容量が必要になる。
- WSL内の `df` だけでなく、WSLの仮想ディスクを置くWindows側の空き容量も確認する。

## 15. 稼働確認用の読み取りコマンド

以下は今回の環境で使った形式です。WSL内で実行する読み取りコマンドであり、復旧や削除は行いません。
環境によってコンテナ名、RESTポート、認証設定は異なります。

```bash
docker inspect api-node-0 broker db rest-gateway \
  --format '{{.Name}} Status={{.State.Status}} ExitCode={{.State.ExitCode}}'

curl --fail --silent --show-error --max-time 10 \
  http://127.0.0.1:3000/node/health
printf '\n'

curl --fail --silent --show-error --max-time 10 \
  http://127.0.0.1:3000/chain/info
printf '\n'

docker logs --since 10m --tail 100 broker
```

`/chain/info` は間隔をあけて複数回確認します。
ブロックが進んでも、直ちにファイナライズが進むとは限りません。
今回も、起動直後は確定位置が同じでしたが、その後エポック209へ進むことを確認しました。

## 16. 関連する別件との切り分け

以前のShare参加時に発生した「ネメシスだけのデータと途中のファイナライズ情報が一致しない」問題とは別の障害です。

| 項目 | Share参加時の問題 | 今回のbroker障害 |
|---|---|---|
| 発生場面 | 別ネットワークへ新規参加するパッケージの使用時 | 稼働していたノードの異常停止後 |
| 主な不整合 | 配布したデータの範囲とファイナライズ情報 | 通知キューの管理位置とメッセージ実体 |
| 基本対応 | 新規参加用のネメシス情報へ整合させる | 既存のローカル履歴から状態・通知・DBを再構築する |

新規参加用の配布データ、途中状態を含むバックアップ、障害後のローカル再構築は、目的が異なります。
一方の修正や手順を、そのまま他方へ適用しないことが重要です。
