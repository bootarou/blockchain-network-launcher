# 高速同期（新規ノード・初回起動前限定）

## 用途

高速同期用パッケージ、または対応フルバックアップのチェーンデータを新しいノードへ取り込み、残りをピアから同期します。
通常のリストアは元ノードの鍵・IDを復元しますが、高速同期は初回Startで新しい鍵・証明書を生成します。
元ノードを残して増設するための機能です。ハーベストや投票の資格・委任は引き継ぎません。

## 対象

- Linux / WSL。初回起動前で、ノード保存先が空であること。
- 単一のnode / broker構成（コンテナの実行ユーザーはroot）、MongoDB 5.0.15の`/dbdata`バインド保存。
- 非PQCの公式・パッチ済み1.0.3.9、または`nftdrive/bnl-catapult-server:1.0.3.9-cf1-ebp`。
- `fileDatabaseBatchSize = 1`、キャッシュDBと検証可能な状態を有効にした構成。
- この機能を含む版のBNLで作成した、高速同期用パッケージまたは互換性情報付きフルバックアップ。

同期途中のノード、起動に一度失敗して鍵・設定が生成された環境、通常リストア後の環境には新たに取り込めません。
既存環境を使う場合は、必要なバックアップを別途確保し、削除範囲を理解したうえで完全初期化するか、別の新規環境を用意します。
既存データを自動削除して取り込む機能ではありません。

## 手順

1. 配布元で「操作」のStopを実行し、node・broker・MongoDB・RESTが正常停止したことを確認します。
2. 配布元のBackupで「書き出すファイルの種類」を「高速同期用パッケージ（配布用）」に変更し、作成します。一覧で完成を待ち、`node-fast-sync-*.zip`をダウンロードします。
3. 新規環境でConfigurationを設定します。公式ネットワークは対応するmainnet/testnetを選択します。カスタムネットワークは先に同じShareパッケージを取り込みます。
4. NodesのHostとFriendly Nameを自分のノード用に設定します。まだStartしません。
5. Backupの「高速同期（新規ノード）」で配布されたZIPを選び、信頼する作成元であることを確認してインポートします。
6. 「取り込み準備完了・初回Start待ち」を待ちます。
7. 「操作」で新しいノード用の暗号化パスワードを入力し、通常のStartを押します。
8. 新しい鍵・証明書と設定を生成した後、互換性を照合し、データを反映して起動します。DashboardでHealth、ブロック高、ファイナライズ、他ノードとの同期を確認します。

取り込んでもConfigurationは書き換えません。元のバックアップのパスワードや秘密鍵を使用して新ノードを復元する機能ではありません。

## 取り込むもの・除外するもの

取り込むのは、ブロック・ステートメント・証明、状態DB、importance、消費済みのblock/state/finalizationキューの管理情報、およびMongoDBデータです。

次の情報は取り込みません。

- `addresses.yml`、生成済み`preset.yml`、配布元のカスタム設定・UIメタデータ
- 証明書・秘密鍵、`harvesters.dat`と委任情報
- 投票用秘密鍵ツリー・投票状態・投票バックアップ
- `transfer_message`、その他の一時キュー、ロックファイル

専用の高速同期用パッケージは、書き出し時にも同じ選別ルールを適用します。設定・鍵ファイルを含めず、MongoDBも必要なストレージファイルに限定し、診断ログ等を除外します。リンク・特殊ファイルがある場合は書き出しを拒否します。通常リストア用のZIPとはファイル名・メタデータを分け、通常リストアでは拒否します。

**フルバックアップを直接渡す場合は、ZIP自体に配布元の秘密情報が残っています。** `addresses.yml`だけを削除して配布しないでください。配布には専用の高速同期用パッケージを使用してください。

専用パッケージにもチェーン上のデータが含まれ、ZIPは暗号化されません。プライベートネットワークの業務データや、チェーン上に保存した機密情報まで匿名化・除去する機能ではありません。

## 検査内容と信頼境界

新しいフルバックアップでは、対応構成・正常停止・brokerキュー消費済みを確認できる場合に限り、`backup-meta.json`へ`fastSync`情報を付けます。
満たさない場合も障害保全用の通常バックアップは作成できますが、高速同期には使用できず、メタデータに理由が記録されます。
専用の高速同期用パッケージでは検査不合格時に作成を拒否します。フルバックアップへ自動的に切り替えることはありません。
保存済みバックアップ一覧にも、高速同期用メタデータの有無と対象外の理由を表示します。

取り込み時はZIP64をディスクへストリーム展開し、取り込むファイルのCRCとサイズ、不正パス・リンク、必要ファイル、ブロック高・先頭と末尾の保存ハッシュ、キューを確認します。
起動時はネットワーク・インフレ設定、ストレージ構成、対応イメージ系統、Nemesis、新旧のCA/transport公開鍵が異なることを再確認します。
nodeデータとMongoDBは組として反映し、失敗時に片方だけを使って起動しません。

これは全ブロックを再実行して状態を再計算する検証ではなく、信頼するスナップショットを利用する方式です。
CRCや保存ハッシュの一致は、作成者の正当性やチェーン全体の正当性を証明しません。未知の配布者・障害後のZIPは使わないでください。
通常リストアの対応範囲は変更しません。旧版のZIPを編集して無理に互換性情報を追加しないでください。

## 容量・中断・失敗

- ZIP保存分、展開後データ分に加え、余裕の空き容量が必要です。空き容量の事前確認と書き込みエラー検出を行いますが、他プロセスによる消費までは予約しません。
- アップロード完了後の展開・検証は、BNLが動作していればブラウザを閉じても継続します。処理中は他の変更操作をブロックします。
- アップロードの途中再開は未対応です。24時間のリクエスト上限と2分のアップロード無通信タイムアウトがあります。プロキシの制限は別途確認してください。
- アップロード・展開中にBNLが停止した場合は、失敗状態で再開します。「取り込みデータを破棄」して最初から取り込み直します。
- 設定不一致でStartが失敗した場合は、設定と操作ログを確認します。準備済みデータは残ります。取り込みの破棄は生成済みノード設定まで削除しません。
- データ反映中の異常終了は「手動確認が必要」となり、Start等をブロックします。`shared/fast-sync.json`とノード保存先の`.fast-sync`を保全してください。記録を削除して解除しないでください。
- `.fast-sync/original-data`と`original-mongo`には反映前の新規ノードのデータを退避します。自動削除しません。

100GB級や実ネットワークの運用前には、その環境での取り込み・起動・同期テストを行ってください。
