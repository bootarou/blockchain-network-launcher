# Debugログとファイルディスクリプター上限

操作ページの「ログ・ファイル上限」で設定します。保存先はマネージャーの
`shared/node-runtime.json` です。保存だけでは稼働中のノードを変更しません。
BNLで「停止 → 起動」を実行すると、通常起動・設定再生成後の起動の両方で反映されます。
初回同期前に保存することもできます。

## Debugログ

- ON: node・broker・自動復旧のコンソールとファイルの閾値をDebugにします。
  既存の個別コンポーネントの閾値もDebugにします。
- OFF: 上記の閾値をInfoにします。以前の個別設定への復元ではありません。
- この画面で一度も保存していない場合、既存のログ設定を維持します。
- ファイル名・出力先・ローテーション容量は変更しません。

Debugはログ量と書き込み量が増えます。再起動で解消する問題を調べる場合は、
再現前から有効にし、停止前後のログを退避してください。
Debugでもローテーションによって古いログは失われるため、全期間の保存を保証しません。
生成済みのログレベルは画面の詳細表示で確認できますが、稼働中プロセスが
読み込んだログレベルを直接照会しているわけではありません。

## nofileとmaxOpenFiles

`nofile` はOSがプロセスごとに適用するFD上限です。ファイルだけでなく
ソケットなども含みます。node・brokerのComposeに既定値65,536を明示し、
Docker側の既定値が1,024であってもその値に依存しないようにします。
UIで65,536～1,048,576の整数を保存でき、soft/hardの両方へ適用します。
この範囲内なら必ず十分という意味ではなく、実際の使用量を監視してください。

復旧用importer・brokerコンテナにも保存済みの上限を適用します。
手動の `docker run` は対象外なので、別途 `--ulimit nofile=65536:65536` が必要です。

画面では以下を区別して表示します。

1. 保存済みの次回起動設定
2. 生成済みComposeの設定
3. コンテナ作成時の設定
4. 稼働中Catapultプロセスの `/proc/<pid>/limits` と現在のFD使用数

停止中は実測値を表示できません。設定変更後はBNLで停止・起動してから
「設定・実測値を更新」で確認してください。既存コンテナの `docker restart` だけでは
コンテナ作成時の上限は変更されません。

`config-node.properties` の `maxOpenFiles` はRocksDB側の設定で、別の値です。
Catapult v1.0.3.9では0の場合、RocksDBの上限を明示的に上書きしません。
今回の画面では読み取り専用にし、DB設定は変更しません。

## 今回の再同期での確認

1. 元データとクラッシュログのバックアップを保持する。
2. 更新したBNLでDebug ON、nofile 65,536を保存する。
3. 新規同期用データ領域とWindows側の空き容量を確保してから起動する。
4. 実測soft/hardが65,536であること、Debugログが出ていることを確認する。
5. 約316万ブロックを越える区間でFD使用数と同期進捗を観測する。
6. 完全同期後、状態とMongoDBの整合性を確認して高速同期用データを作成する。

FD不足によるクラッシュと、再起動で回復したファイナライズ同期停止は別の問題です。
この対策で後者の修正や再現性まで保証するものではありません。

## 検証

`cd backend && npm run test:runtime` で設定検証、ログ閾値、設定再生成後の再適用、
実測値と設定値の区別をテストします。Linux/Dockerでの実動作確認は別途必要です。
